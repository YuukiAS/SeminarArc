# 0.1.2 Recording State 与 One-active-seminar Invariant 结果

## 实际修改内容

- 新增 `StartSeminarSessionResult`、`ActiveSeminarSessionState`、`ActiveSeminarSession` 和 `SeminarSessionRecoveryReason`，用于表达 start session 的非 Boolean 结果语义。
- 新增 `DatabaseTransactionRunner` 与 `RoomDatabaseTransactionRunner`，生产环境通过 `AppDatabase.withTransaction` 执行 repository 状态转换，测试中可替换为 fake runner。
- 扩展 `SeminarDao`：
  - `getSeminarsByStatus(status)`：查找当前 `ACTIVE` seminar。
  - `markDraftSeminarActive(...)`：仅当目标 seminar 仍是 `DRAFT` 时条件更新为 `ACTIVE`。
- 扩展 `RecordingDao`：
  - `getLatestRecordingForSeminar(seminarId)`。
  - `getLatestRecordingByState(seminarId, state)`。
- 扩展 `SeminarRepository`：
  - `getActiveSeminarSessionState()`。
  - `startSeminarSession(seminarId)`。
- 在 `SeminarRepositoryImpl` 中集中实现 one-active-seminar invariant。
- 更新 Hilt binding，把 `RoomDatabaseTransactionRunner` 绑定为 `DatabaseTransactionRunner`。
- 新增 repository unit tests 覆盖本阶段 required scenarios。

## 数据模型与状态机语义

本阶段继续使用 schema version 1，不新增表、不改字段。

- seminar session 状态由 `SeminarEntity.status`、`sessionStartedAt`、`sessionEndedAt` 表达。
- recording 查询边界由已有 `RecordingEntity.state` 表达，供后续 foreground service 接入。
- `StartSeminarSessionResult` 语义：
  - `Started`：当前没有 active seminar，目标 `DRAFT` seminar 被启动。
  - `AlreadyActive`：目标 seminar 已经是唯一有效 active session。
  - `AnotherSeminarActive`：已有另一场有效 active seminar，当前 seminar 不会被启动。
  - `RecoveryRequired`：数据库存在 stale / inconsistent active state，repository 不静默覆盖。
  - `CannotStart`：目标 seminar 状态不是 `DRAFT`，无法开始。
  - `NotFound`：目标 seminar 不存在。
- stale / conflict reason：
  - `ACTIVE_WITHOUT_START_TIME`。
  - `ACTIVE_WITH_END_TIME`。
  - `MULTIPLE_ACTIVE_SEMINARS`。
  - `LOST_UPDATE`。

## DAO / Repository API

- `SeminarDao.getSeminarsByStatus(status)` 用于读取当前 active seminar 集合。
- `SeminarDao.markDraftSeminarActive(...)` 使用 `WHERE id = :seminarId AND status = :draftStatus` 避免把非 draft seminar 直接覆盖成 active。
- `SeminarRepository.getActiveSeminarSessionState()` 返回当前 active session、none 或 recovery 状态。
- `SeminarRepository.startSeminarSession(seminarId)` 是后续 UI / foreground service 启动 session 的统一入口。

## One-active Invariant 如何保证

- `startSeminarSession` 在 `transactionRunner.withTransaction` 内执行。
- 启动前先读取所有 `ACTIVE` seminar：
  - 0 个 active：只允许目标 `DRAFT` seminar 通过条件 update 进入 `ACTIVE`。
  - 1 个 active 且是当前 seminar：返回 `AlreadyActive`，不重复创建。
  - 1 个 active 但不是当前 seminar：返回 `AnotherSeminarActive`，不修改当前 seminar。
  - 多个 active 或 active 记录缺失/冲突 session 时间：返回 `RecoveryRequired`，不覆盖。
- 条件 update 返回 0 行时返回 `LOST_UPDATE`，用于表达事务内状态竞争或失败路径。

## 新增测试

更新 `SeminarRepositoryImplTest`，新增覆盖：

- 没有 active seminar 时启动当前 draft seminar，并验证 DB facts。
- 当前 seminar 已 active 时返回 `AlreadyActive`，不重复 update。
- 另一个 seminar 已 active 时返回已有 active seminar 信息，当前 seminar 保持 `DRAFT`。
- stale active seminar 缺少 `sessionStartedAt` 时返回 `RecoveryRequired`。
- 多个 active seminar 时返回 `MULTIPLE_ACTIVE_SEMINARS` conflict。
- 条件 update 失败时返回 `LOST_UPDATE` recovery，并验证没有错误覆盖。

## 进入 Foreground Service 前需要知道的事项

- 后续 service / ViewModel 必须通过 `SeminarRepository.startSeminarSession(seminarId)` 获取 session 语义，不能自行设置 `SeminarStatus.ACTIVE`。
- UI 下一阶段应处理 `AnotherSeminarActive`，例如导航到已有 active seminar。
- UI 下一阶段应处理 `RecoveryRequired`，例如展示恢复/冲突处理入口；不要自动覆盖 active 记录。
- 真实录音接入时应在 repository/use case 层继续使用 transaction runner，把 `RecordingEntity` 状态转换与 seminar session 状态保持一致。
