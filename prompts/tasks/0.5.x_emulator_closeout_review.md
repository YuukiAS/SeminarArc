# 0.5.x Emulator Closeout Review

## 结论

本轮 defer 是测试路由/设备隔离策略阻塞，不是 `0.5.x` 代码质量失败。

当前 `0.5.x` 已达到 `HEADLESS_ALPHA_CANDIDATE`：Room v7 formula schema/domain、formula region selection/edit、manual LaTeX durable queue、provider capability/status、READY formula export、BibTeX/RIS、internal APK build/signature/secret scan 均已有本地通过证据。

唯一缺口是 Windows Emulator instrumentation closeout，因此尚不能创建 `v0.5.0-alpha.1` tag / version CI / GitHub prerelease。

## 本轮 defer 证据成立

Windows ADB inventory：

- `8cc54656 unauthorized`
- `emulator-5554 device`

旧 policy 禁止在 inventory 中存在 physical serial 时运行 Gradle `connected*AndroidTest`，因此没有执行 connected task、没有 tag/release，是正确的保守行为。

## 复核后的改进判断

当前 blocker 不要求恢复、授权或操作 GM1910。

真正需要避免的是 **unscoped device enumeration / install chain**。如果所有会安装 APK、启动 instrumentation 或注入 UI 的命令都显式使用 `-s emulator-5554`，并且绝不对 physical serial 执行命令，则可以建立一个更窄的 `explicit-emulator-only` 验收通道。

因此下一任务不得直接运行：

- `connectedDebugAndroidTest`
- `connectedAndroidTest`
- 任何会自行枚举并安装到所有可见 device 的 Gradle connected/device task

而应：

1. 只读 `adb devices -l` 确认 `emulator-5554` 为 `device`；physical serial 即使仍显示 unauthorized/offline，也只记录、不操作。
2. 用 Gradle **仅构建** app APK / androidTest APK，不执行 connected install。
3. 检查实际 APK/package/test package/runner。
4. 所有设备写操作显式使用 `adb -s emulator-5554 ...`。
5. 显式安装 app APK 和 test APK 到 Emulator。
6. 显式 `adb -s emulator-5554 shell am instrument ...` 运行 instrumentation suite。
7. 对 internal APK install/launch/update smoke 同样只使用 `-s emulator-5554`。
8. 前后只读 inventory，确认没有对 GM1910 做 transport/package 操作。

这个通道在安全意义上比运行 unscoped `connectedDebugAndroidTest` 更窄，不需要改变 physical USB/ADB transport。

## 命令超时策略

此前出现长时间静默等待。下一任务必须：

- 外部进程使用短轮询，建议 15-30 秒一次；
- 每轮输出当前状态；
- 普通 adb/package 命令应有约 30-60 秒 hard timeout；
- instrumentation/Gradle 可有更长总预算，但必须轮询，不允许超过 60 秒完全无状态输出；
- 到总 timeout 后终止当前 Emulator-side command，记录证据并继续可安全诊断，不无限等待。
