# Phase 2：实现 WorkManager processing queue

如果 audit 确认尚未有可靠 background queue，则为 OCR 与 image enhancement 建立 WorkManager-backed durable queue。

建议采用统一但不过度抽象的处理架构：

UI / ViewModel
→ use case / processing repository
→ `ProcessingJob`
→ WorkManager worker
→ provider
→ app-owned result / derived asset

## 必须满足

### Job state

真实支持：

- `QUEUED`
- `RUNNING`
- `SUCCEEDED`
- `FAILED`
- `CANCELLED`

### Idempotency

同一 asset + operation + equivalent options 的重复请求不得无限创建重复工作。

可使用 stable job identity / unique work / existing-result short-circuit 等合理方案。

### Retry

失败 job 如果 `retryable=true`，UI/use case 可以明确重试。

重试：

- 不覆盖原图；
- 不产生无限 duplicate jobs；
- previous failure 保留可诊断事实或以清晰规则更新；
- output 只有真实可读后才能 success。

### Cancel

用户可以取消 queued/running job。

取消后：

- WorkManager work 被取消；
- durable job 进入 `CANCELLED`；
- partial derived file 清理；
- original asset/result 不受影响。

### Process recovery

app/process restart 后：

- queued work 可继续；
- WorkManager running/retry semantics 与 Room job 状态不产生长期矛盾；
- 遗留非法 RUNNING 状态有明确 reconciliation；
- UI 从 Room/WorkManager durable facts 恢复，不依赖 Activity memory。

### Worker source of truth

worker input 应尽量使用 job ID / asset ID，而不是把 raw file path 作为唯一事实来源。

worker 执行时重新从 Room/storage 读取当前事实。
