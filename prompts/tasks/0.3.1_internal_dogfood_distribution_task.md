# 0.3.1 Internal Dogfood Distribution Task

## Goal

在已完成的 `0.3.x` 基础上建立 SeminarArc 第一条可重复的 internal APK 分发链：**Windows 本地构建/验收/签名，版本 tag 触发一次 GitHub Actions 远端验收，GitHub Release 作为用户下载入口**。

本 task 不进入 `0.4.x` 功能开发。

## Baseline

- `0.3.x COMPLETE`，`origin/main` 至少包含 `ede1cb0d9d123c4cbe1f7408b640fe361d702b1b` 或更晚。
- Windows Emulator `Pixel_8` API 36 connected regression 已可用。
- Windows implementation/release checkout：`D:\Code\SeminarArc-emulator`。
- Windows SDK：`D:\Android\Sdk`。
- JDK 17：`D:\Code\_jdks\jdk-17.0.20.1+1`。
- 当前 GitHub Releases 为空；需要创建第一条 internal prerelease。
- 当前 `versionName` 仍有陈旧值，必须修正。
- GitHub Actions policy 见 `docs/CI_POLICY.md`：普通 push/docs 不跑，只在 `v*` tag 或手动触发时运行。

## Required work

### 1. Versioning

建立重复可用的 Android versioning convention。

第一版使用：

- tag: `v0.3.1-internal.1`
- versionName: `0.3.1-internal.1`
- versionCode: 单调递增整数

要求：

- 修正陈旧 `0.1.5-dev`；
- 后续 `0.4.x-internal.*` / `0.5.x-alpha.*` 同样按 milestone 发布；
- internal signing 与未来 Google Play production signing 分离。

### 2. Internal application identity

建立独立 internal application id，优先：

`com.yuukias.seminararc.internal`

可使用 `applicationIdSuffix = ".internal"` 或等价简单实现。内部版本应有可辨识 app label；不要引入不必要的多 flavor 复杂度。

### 3. Local release build

APK 必须在受控 Windows 本地环境编译，不依赖 GitHub-hosted runner 作为 APK 构建源。

在 clean release commit 上至少执行：

```powershell
.\gradlew.bat testDebugUnitTest
.\gradlew.bat assembleInternal
.\gradlew.bat lintDebug
.\gradlew.bat compileDebugAndroidTestKotlin
```

如果实际 build type/task 名不同，按实现后的真实名称调整并记录。

随后：

- Windows ADB safety gate，只允许 `emulator-*`；
- Windows Emulator connected regression；
- internal APK install/launch smoke；
- package/applicationId/version inspection；
- APK secret scan/basic package inspection；
- 计算 SHA-256。

GM1910 不参与。

### 4. Signing

绝不提交 keystore/private key/password。

目标是稳定 internal signer，使后续 Release APK 可以原地覆盖升级并保留数据。

优先策略：

- signing key 保存在 Windows 本地、repo 之外；
- Gradle 通过环境变量或 repo 外 local properties 读取路径/alias/password；
- 不要求 GitHub Actions Secrets；
- GitHub 只接收已经签名完成的 APK 二进制，不接收私钥。

如果当前没有稳定 internal signer：

- 可以先完成 build variant、release pipeline、文档和 disposable smoke APK；
- 若创建新的稳定 internal signing key 需要用户批准，明确记录为一次性 human action；
- 不因此阻塞 `0.4.x/0.5.x` 其他开发。

### 5. Version-tag remote CI

GitHub Actions 不是每次 push CI，而是版本级远端独立验收。

在本地 release gate 全部通过、实现/docs 已 commit + push 后：

1. 确认 intended release commit 与 `origin/main` 对齐；
2. 创建 `v0.3.1-internal.1` tag；
3. push tag；
4. tag 自动触发 `.github/workflows/android.yml`；
5. 远端必须至少通过 `testDebugUnitTest assembleDebug lintDebug`；
6. CI PASS 后才创建 GitHub prerelease。

如果 GitHub 基础设施瞬时失败，可重跑 version gate。不要为 CI 制造新的空 commit；文档/普通 push 不应触发 Actions。

### 6. GitHub Release distribution

用户已明确授权：可以把本 task 生成的 **SeminarArc internal APK、SHA-256/checksum 和 release notes** 上传到本仓库 GitHub Release。除此之外不得上传用户数据、测试媒体、keystore 或 secret。

CI PASS 后创建 GitHub prerelease：

`v0.3.1-internal.1`

Release assets 至少包含：

- `SeminarArc-0.3.1-internal.1.apk`
- `SeminarArc-0.3.1-internal.1.apk.sha256`

Release notes 至少写：

- internal dogfood；
- commit SHA；
- application id；
- versionName/versionCode；
- 主要已完成功能；
- 本地 test/Emulator gates；
- remote version CI status；
- known limitations；
- sideload/update 注意事项。

优先通过本地 `gh release create` / `gh release upload` 或等价 GitHub API 上传。不要使用 Actions artifact 作为用户下载入口。

### 7. Emulator validation

使用 Windows Emulator：

- internal APK install/launch：PASS；
- v4 database/app startup：PASS；
- `0.1.x/0.2.x/0.3.x` connected suite：PASS；
- internal application id 与普通 package 不冲突。

### 8. Installation docs

创建 `docs/INTERNAL_DISTRIBUTION.md`，用中文说明：

- 用户去 GitHub `Releases` 页面下载，不去 Actions；
- 选最新 internal/prerelease 的 `.apk` asset；
- SHA-256 校验（可选）；
- Android 侧载和“安装未知应用”最小授权；
- 首次安装与 update-in-place；
- 相同 applicationId + 相同 signing key 才能保留数据升级；
- internal 与未来 production build 的区别；
- 卸载会清除 internal app data。
