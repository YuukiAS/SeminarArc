# 0.3.1 Internal Dogfood Distribution Task

## Goal

在已完成的 `0.3.x` 基础上建立 SeminarArc 第一条可重复的 internal APK 分发链：用户无需本地 build，即可从 GitHub 下载 APK 并在个人 Android 手机侧载安装。

本 task 是 release/distribution foundation，不进入 `0.4.x` transcription/summary/Notion 功能开发。

## Baseline

- `0.3.x COMPLETE`，最终功能提交至少包含 `ede1cb0d9d123c4cbe1f7408b640fe361d702b1b` 或更晚。
- Windows Emulator `Pixel_8` API 36 connected regression 已可用。
- 当前 CI `.github/workflows/android.yml` 会 `assembleDebug` + unit tests，但没有上传 APK artifact。
- 当前 `app/build.gradle.kts` 的 `versionName` 仍是陈旧的 `0.1.5-dev`，必须修正。

## Required work

### 1. Versioning

Define and document a repeatable Android versioning convention.

For the first dogfood artifact, use an explicit internal prerelease version such as `0.3.1-internal.1` (or a better equivalent if the current build configuration makes another naming convention clearly preferable).

Requirements:

- increment `versionCode` monotonically;
- remove stale `0.1.5-dev` metadata;
- document how future `0.4.x-internal`, `0.5.x-alpha`, and `0.9.x` versions advance;
- do not conflate internal dogfood signing with eventual Google Play production signing.

### 2. Internal application identity

Prefer a distinct internal application id/build variant so dogfood builds can coexist with a future production Play install.

Recommended direction:

- internal variant/build type with `applicationIdSuffix = ".internal"` or equivalent;
- visible app name should make clear that it is an internal build when practical;
- production namespace/source code remains unchanged.

Do not create unnecessary multi-flavor complexity if a simpler safe build type achieves the same result.

### 3. GitHub Actions downloadable APK

Update GitHub Actions so a successful internal packaging run uploads an APK artifact using current supported GitHub Actions upload-artifact tooling.

The artifact should have a stable, human-readable name containing SeminarArc and the version.

Required gates before artifact upload:

- `testDebugUnitTest` or equivalent unit gate;
- internal APK assemble;
- lint;
- `git diff --check` locally before commit;
- package/version inspection;
- basic APK secret scan for obvious committed credentials/tokens/endpoints that should not ship.

Keep ordinary CI useful; do not make a transient external metadata API smoke a prerequisite for producing the artifact.

### 4. Signing design

Do NOT commit any keystore/private key/password.

Implement configuration that can support a stable internal signing key injected from environment/GitHub Actions secrets.

If required secrets are not currently provisioned:

- prepare the Gradle/workflow contract and exact secret names;
- make the missing stable signer explicit in the result;
- do not fabricate or commit a key;
- do not block the rest of the repository roadmap if a disposable debug artifact can still be safely produced for one-off smoke.

The preferred durable state is:

- stable internal application id;
- stable internal signer in GitHub Actions secrets;
- subsequent internal APKs update in place without uninstall/data loss.

Provisioning/changing the private signing key or repository secrets is a human-approval boundary unless the user has explicitly authorized a trusted local Codex session to perform it without exposing the secret.

### 5. Emulator validation

Use Windows Emulator only for connected/instrumentation validation.

GM1910 must not be used.

At minimum validate:

- internal package installs/launches on Emulator;
- v4 database/app starts normally;
- existing `0.1.x`/`0.2.x`/`0.3.x` connected suite still passes;
- internal application id does not accidentally collide with the normal package if both are present.

Connected preflight must confirm Windows ADB only sees `emulator-*`.

### 6. Installation documentation

Create:

`docs/INTERNAL_DISTRIBUTION.md`

Document in Chinese:

- where the GitHub Actions artifact appears;
- artifact filename;
- whether GitHub wraps it in ZIP;
- Android sideload steps;
- “Install unknown apps” prompt;
- first install versus update-in-place behavior;
- data retention implications if signing identity changes;
- how to distinguish internal vs eventual production build;
- how to verify version in the app/package if a version surface exists;
- how to safely remove the internal build later.

Do not tell the user to disable broad Android security settings beyond what is needed for one app/browser/file-manager to install an APK.
