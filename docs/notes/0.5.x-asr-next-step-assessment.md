# SeminarArc 本地 ASR 下一步评估

## 结论

现在不应直接把 whisper.cpp 和模型打进 Android APK。更稳妥、信息增益更高的下一步，是先在 workstation 建立 **完全离线、异步、可复现** 的 whisper.cpp benchmark；只有性能、内存、时间戳质量和实际 seminar 准确度达到门槛后，再创建 Android provider integration task。

这不是否定 Android 本地 ASR。whisper.cpp 上游确实提供 Android 示例，并建议移动端优先从 tiny/base 模型开始；上游也提供 encoder benchmark 和完整模型/音频 benchmark 入口。当前缺口是 SeminarArc 自己的双语 seminar、长音频、目标设备、电量和 APK 分发证据，而不是缺少一个可以编译的 demo。

上游参考：

- [whisper.cpp Android example](https://github.com/ggml-org/whisper.cpp/tree/master/examples/whisper.android)
- [whisper.cpp benchmark tool](https://github.com/ggml-org/whisper.cpp/tree/master/examples/bench)
- [whisper.cpp main benchmark guidance](https://github.com/ggml-org/whisper.cpp#benchmarks)

## 当前私有录音事实

- 数量：2 段 MP3。
- 总大小：22,304,613 bytes。
- 总时长：557.615 秒，约 9.3 分钟。
- 2/2 可读取时长、码率、采样率和声道元数据。
- 当前产品没有外部录音导入入口，因此这些文件只是 ignored benchmark corpus，不是 recording product-flow 证据。
- 没有真实 ASR runtime，也没有可用于计算 WER/CER 的人工标注全文。

## 为什么先做 workstation benchmark

1. 可以在不改变 APK、签名、安装体积和移动端生命周期的情况下比较多个 multilingual/quantized 模型。
2. 私有录音始终留在本机；模型、输出和日志也可放在 ignored evidence 目录。
3. 能先验证 MP3 decode、长音频切片、时间戳连续性、语言混合和 provider output normalization，再把稳定 contract 接到现有 durable queue。
4. Android Emulator 不能代表真实 ARM 手机的速度、温度、电量或后台限制；在没有真机授权时，直接做 Android 性能结论会产生伪证据。
5. Mac mini 只有在它已经是可用执行节点、或后续明确选择它作为常驻本地转写服务时才有额外价值；当前 Windows/workstation 先行不需要新增硬件或网络服务。

## 下一张最小任务

建议任务名：`0.6.x_local_asr_workstation_benchmark`。

任务只做离线 benchmark adapter，不接 UI、不改 production provider binding：

1. 固定 whisper.cpp revision、构建参数和模型文件 SHA-256。
2. 选择 multilingual tiny/base 与至少一个量化候选；模型大小以实际下载 artifact 记录，不在计划中硬编码。
3. 对公开短样本先验证安装和输出 schema，再对 ignored 私有录音运行。
4. 记录每段音频的 decode 时间、总推理时间、real-time factor、峰值 RSS、线程数、模型加载时间、segment 数、首尾时间戳和失败类型。
5. 从私有录音各选 60–120 秒代表片段，在 private evidence 中人工标注，用于中英文专名、口音、投影环境噪声的 WER/CER/主观可用性比较；tracked 结果只保留聚合指标。
6. 验证输出能映射到现有 `TranscriptionProvider` timestamped segments，但不写 Room、不修改 app data。
7. 所有音频、模型、转写全文和逐句误差保持 ignored，不上传第三方。

## 进入 Android 实现前的决策门槛

必须先回答：

- 选定模型在目标语言组合上的准确度是否足以支持 seminar review，而不是只产生非空文本；
- 长音频是否需要 chunk/overlap/VAD，以及 segment 时间戳能否保持单调、可用于 timeline window；
- workstation 与目标 ARM Android 的预计 real-time factor、峰值内存和模型加载开销；
- 模型是随 APK、首次本地下载，还是由用户显式选择本地文件；每种方案的体积、license、checksum 和失败恢复；
- 前台/后台执行、充电/电量、热管理、WorkManager 约束和取消语义；
- 模型/Native ABI 对 APK/AAB、Play policy 与 internal signer 的影响。

只有这些证据成立，才应实现 `WhisperCppTranscriptionProvider`、Native binding、模型管理和 Android instrumentation。最初 Android task 也应限定 internal/dogfood，默认 unavailable provider 继续作为 production-safe fallback。
