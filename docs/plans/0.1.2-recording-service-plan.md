# SeminarArc 0.1.2 Recording Service Plan

Status: planned

Target version: `0.1.2`

## Goal

Implement a reliable local foreground recording session for one active seminar, with recoverable Room state, persistent notification, and full-recording playback.

This phase establishes the service truth needed by all later capture, timeline, and clip work.

## Inputs

- Completed `docs/plans/0.1.1-closeout-plan.md` gate.
- `TODO.md` recording and local-first constraints.
- `docs/plans/0.1.x-mvp-implementation-plan.md`.
- Existing `recording`, `media`, `data`, `domain`, `ui`, `di`, and `util` packages.
- Android skill references for architecture, data layer, background work, testing, security, and accessibility.
- Compose references for state management, navigation, Material 3 theming, and accessibility.

## Scope

In scope:

- Foreground service for seminar audio recording.
- Recording notification channel and persistent ongoing notification.
- Runtime microphone and notification permission flow.
- One-active-seminar invariant.
- Recording state persisted in Room.
- Recovery after Activity recreation, process death, abnormal stop, and stale `ACTIVE` state.
- Full recording storage under the seminar-owned directory.
- Media3 playback for full recordings.
- UI routes for start/resume, active recording, and stale recovery.
- Tests with fake recorder/controller where hardware is not required.

Out of scope:

- Pause/resume unless it is proven stable enough in this phase.
- Direct notification stop action unless the stop flow is unambiguous and safe.
- CameraX photos.
- Timeline notes/questions/photos during recording, except minimal mark action if needed for notification affordance.
- Clip generation.
- Transcription, summary, OCR, cloud upload, and provider interfaces beyond placeholders needed for clean boundaries.

## Architecture Decisions

- `RecorderController` remains the domain-facing contract for recording operations.
- The foreground service owns the actual recorder lifecycle.
- Room stores durable recording/session facts: seminar status, recording state, file path, start time, duration when finalized, and failure state.
- ViewModels derive UI state from repositories and service/session state, not Activity fields.
- Notifications deep-link back to the active session route.
- Permission denial must route to a real state that still allows browsing existing seminar content.

## Work Breakdown

### 1. Session model audit and additions

Check whether current schema can represent:

- `DRAFT`, `ACTIVE`, and `COMPLETED`.
- Active session start time.
- Current recording row with `RECORDING`, `COMPLETED`, or `FAILED`.
- Recording file relative path.
- Failure reason and recoverability, if currently missing.

If schema changes are needed in `0.1.2`, define a Room migration rather than destructive reset once real user data may exist.

### 2. One-active-seminar enforcement

Implement repository/use-case behavior:

- Starting a draft seminar first checks whether another seminar is active.
- If another seminar is active, navigation returns to that session.
- Starting the same active seminar resumes the active screen.
- Abnormal stale state routes to a recovery screen instead of silently overwriting.

Validation:

- Unit tests for starting with no active seminar, same active seminar, different active seminar, and stale active state.

### 3. Foreground service and notification

Implement:

- Manifest service declaration with the correct foreground service type.
- Required permissions for microphone and foreground service behavior.
- Notification channel for active recording.
- Ongoing notification showing app name, seminar title, elapsed time or active state.
- Return-to-session action.
- Optional mark action only if it can write a durable event immediately.

Validation:

- Service starts only after permission checks.
- Notification remains ongoing while recording.
- Deep link or pending intent opens the active session.

### 4. Recording storage and lifecycle

Implement:

- Recording file creation under `files/seminars/<seminar-id>/recordings/`.
- Relative path persistence.
- Safe finalize path that writes duration and completed state.
- Failure path that preserves diagnostic state without deleting unrelated assets.
- Cleanup path when a seminar is deleted.

Validation:

- Unit/integration tests for file path ownership and deletion orchestration.
- Manual or instrumented smoke test for recording start/end when a device is available.

### 5. Active recording UI

Implement:

- Active session route from detail.
- Seminar identity header.
- Recording timer/status.
- End seminar action with serious confirmation.
- Permission denied state.
- Stale recovery state.
- No fake photo/clip controls unless clearly disabled or labeled as future.

Compose requirements:

- UI state uses sealed types for loading/ready/error/recovery.
- Events use `SharedFlow(replay = 0)`.
- Public composables expose `modifier`.
- Buttons are 48dp minimum and use Material/SeminarArc tokens.

### 6. Full recording playback

Implement:

- Media3-backed full recording playback after completion.
- Detail/timeline entry point showing duration and playable state.
- File-missing failure state that preserves the rest of the seminar.

Validation:

- Playback only appears when a completed recording file exists.
- Missing file shows a recoverable error, not a crash.

## Verification Gate

Do not start `0.1.3` until:

- One-active-seminar invariant has unit coverage.
- Recording can start and end through foreground service in at least emulator or documented local conditions.
- App recovery does not rely on Activity memory.
- Full recording can be played after seminar completion.
- Permission denied and stale active states are represented in UI.
- No CameraX/photo-only UI is claimed as complete.

## Risks

- Android 14+ foreground service permission and type requirements may need exact policy review before release.
- Long-running real-device recording cannot be fully validated without device access.
- Audio focus, calls, Bluetooth, and background restrictions may reveal follow-up tasks.
