Status: planning entry point

Last updated: 2026-07-19

## Purpose

This file indexes the executable planning sequence for developing SeminarArc after the current roadmap refresh. It does not authorize implementation by itself.

The product source of truth remains `TODO.md`. The detailed local-first MVP contract remains `docs/plans/0.1.x-mvp-implementation-plan.md`. The first implementation batch record remains `docs/plans/0.1.x-mvp-execution-batch-01.md`.

Future Codex implementation work must still be split into `prompts/tasks/*_task.md` before execution, following `AGENTS.md` and `prompts/AGENT_RULES.md`.

## Current Baseline

The repository is currently at `0.1.1-dev`.

Already present:

- Android/Compose single-module app baseline.
- Material 3 theme and SeminarArc design-token mapping.
- Room schema for `SeminarEntity`, `RecordingEntity`, `TimelineEventEntity`, and `AudioClipEntity`.
- Seminar list, editor, and detail flows.
- Abstract PDF import, replace, remove, and app-private storage ownership.
- CI workflow skeleton for debug build and unit tests.

Not yet claimed:

- Verified clean local build.
- Verified CI quality beyond the workflow skeleton.
- Foreground recording service.
- Real active session recovery.
- CameraX photo capture.
- Timeline event creation during recording.
- Clip generation, fallback, and retry.
- Final local MVP acceptance.

## Plan Sequence

Execute these plans in order. Do not skip a gate unless a later task records the reason and gets explicit human approval.

1. `docs/plans/0.1.1-closeout-plan.md`
   - Audit and close the current `0.1.1-dev` foundation.
   - Primary output: a verified baseline that builds, tests, and does not misrepresent future features.

2. `docs/plans/0.1.2-recording-service-plan.md`
   - Implement reliable foreground recording, one-active-seminar enforcement, recovery, and full-recording playback.
   - Primary output: a real recording session that survives normal Android lifecycle disruption.

3. `docs/plans/0.1.3-capture-timeline-plan.md`
   - Implement live capture, CameraX photos, photo-only mode, notes/questions/marks, and unified timeline playback anchors.
   - Primary output: the core offline seminar capture loop.

4. `docs/plans/0.1.4-clip-playback-resilience-plan.md`
   - Implement marked clip generation, WorkManager processing, failure states, retry, and full-recording fallback.
   - Primary output: clip behavior that never pretends unfinished media is playable.

5. `docs/plans/0.1.5-local-mvp-export-acceptance-plan.md`
   - Implement Markdown/ZIP export, final data cleanup tests, docs, CI hardening, and full local MVP acceptance.
   - Primary output: the first durable local-first MVP.

6. `docs/plans/0.2.x-reconstruction-readiness-plan.md`
   - Prepare post-MVP Research Reconstruction, OCR/provider architecture, migrations, and design changes.
   - Primary output: a reviewed bridge into `0.2.x`, not implementation inside `0.1.x`.

## Cross-Cutting Rules

- Keep `0.1.x` focused on local capture, timeline, playback, export, and cleanup.
- Do not add AI, OCR, transcription, Notion, ads, subscriptions, login, or cloud sync to `0.1.x`.
- Every asset must be owned by one `seminarId`.
- At most one seminar may be `ACTIVE`.
- Recording truth must come from persistent service/database state, not Activity memory.
- Timeline events captured during a session must store recoverable recording offsets.
- Clip UI must respect `PENDING`, `PROCESSING`, `READY`, and `FAILED`; only `READY` clips are playable.
- Deletion must keep Room records and app-owned files consistent.
- Compose UI must remain in the `Academic Archive` direction: list-first, quiet, dense enough for repeated use, Material 3 token-backed, accessible, and free of fake completion paths.

## How To Convert A Plan Into Work

For each implementation step:

1. Create a focused `prompts/tasks/<id>_task.md`.
2. Include frontmatter for allowed actions, network, shell commands, code edits, and human approval needs.
3. Reference exactly one plan file plus any directly required supporting files.
4. Keep the task small enough to produce a reviewable diff.
5. Require Codex to write `prompts/tasks/<id>_result.md` after execution.

Do not use this index or any plan document as a direct executable task.
