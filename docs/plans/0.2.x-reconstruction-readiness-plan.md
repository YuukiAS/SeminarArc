# SeminarArc 0.2.x Reconstruction Readiness Plan

Status: readiness gate passed

Target line: `0.2.x`

## Goal

Prepare the transition from local capture MVP to local visual reconstruction and research-oriented post-seminar workflows.

This plan is deliberately not part of the `0.1.x` MVP execution path. It exists so that `0.1.x` implementation can avoid accidental AI/provider/schema overreach while still preserving a clear future architecture.

## Inputs

- Completed `0.1.5` local MVP.
- `TODO.md` sections for data model evolution, provider architecture, Research Reconstruction, and post-`0.1.x` roadmap.
- `design/` updates after the live capture and timeline UI exist.
- Privacy/security review for any provider or third-party SDK.

## Scope

In scope for planning:

- Room migration strategy from the `0.1.x` schema.
- Unified seminar asset model.
- Processing job model.
- Local image enhancement and OCR provider boundary.
- Research Reconstruction workspace information architecture.
- Provider interfaces for OCR, transcription, summary, references, export, and cloud upload policy.
- License and privacy review checklist.

Out of scope for this plan:

- Implementing OCR.
- Implementing transcription.
- Implementing Notion.
- Calling live provider APIs.
- Adding cloud upload.
- Adding ads or payment.

## Proposed Data Evolution

Candidate entities to design before implementation:

- `SeminarAssetEntity`
  - Unified identity for abstract, recording, photo, enhanced photo, clip, export, and future derived assets.
  - Stores seminar ownership, asset type, relative path, origin asset ID, created time, and deletion state if needed.

- `ProcessingJobEntity`
  - Tracks local/remote jobs such as OCR, photo enhancement, transcription, summary, reference lookup, and export.
  - Stores provider ID/version, input asset IDs, state, timestamps, retryability, and readable error.

- `OcrResultEntity`
  - Stores text blocks, confidence, provider, human correction state, and link back to photo asset.

- `TranscriptSegmentEntity`
  - Stores recording ID, start/end offsets, speaker label, language, text, provider, and correction state.

- `ReferenceCandidateEntity`
  - Stores candidate metadata, source, match score, reason, confirmed/rejected status, and DOI where available.

- `TagEntity` and mapping tables
  - Supports system tags such as `KEY_SLIDE`, `BACKGROUND`, `METHOD`, `RESULT`, `REFERENCE`, `FORMULA`, and `FOLLOW_UP`, plus user tags.

- `ExportRecordEntity`
  - Stores export format, target, timestamp, included media, and externally exported-copy semantics.

All schema changes must have explicit Room migrations and cannot use destructive migration for real user data.

## Provider Boundary

Design provider interfaces before adding implementations:

- `TextOcrProvider`
- `FormulaOcrProvider`
- `TranscriptionProvider`
- `SummaryProvider`
- `ReferenceLookupProvider`
- `ExportProvider`
- `CloudUploadPolicy`

Rules:

- Providers cannot be called directly from Compose UI.
- Provider output must map into app-owned domain models.
- Raw provider responses are optional cached artifacts, not the only source of truth.
- Every cloud upload is user-triggered and shows scope, provider, cost, and privacy impact.
- App-owned commercial API secrets must not be embedded in the APK.

## Research Reconstruction Workspace

The workspace should remain scoped to one seminar.

Recommended flow:

1. Select or confirm key slides.
2. Run local OCR on selected photos.
3. Optionally mark formula regions for formula recognition.
4. Extract possible title/author/DOI/method/dataset clues.
5. Look up open metadata candidates.
6. Let the user confirm or reject references.
7. Draft an editable Seminar Brief.
8. Export Markdown/ZIP and optionally send to later integrations.

Design rules:

- Do not replace the unified timeline.
- Do not place the entire transcript into timeline rows.
- Show candidate confidence and review state.
- Treat all AI/provider output as editable draft or candidate content.

## Technical Spikes Required Before Implementation

Before creating `0.2.x` implementation tasks, run small research or audit tasks for:

- ML Kit Text Recognition language support, model packaging, offline behavior, and licensing.
- OpenCV or Android-native image transform options for crop, rotate, perspective correction, and enhancement.
- Room migration design from schema version 1.
- Storage growth and thumbnail strategy.
- OCR job cancellation/retry/idempotency.
- Privacy wording for local OCR versus cloud OCR.
- Crossref/OpenAlex/Semantic Scholar API terms before any reference lookup implementation.

## 2026-08-30 Readiness Gate Result

Phase A readiness is complete and the gate is passed for `0.2.x` production implementation.

Decisions:

- Room migration starts from current schema version `2` and advances to explicit version `3`.
- Existing `seminars`, `recordings`, `timeline_events`, and `audio_clips` remain the source-compatible `0.1.x` tables.
- `MIGRATION_2_3` may add `seminar_assets`, `processing_jobs`, `ocr_results`, `tags`, and `asset_tags`, then idempotently backfill assets from existing abstract PDF, recording, photo timeline, and ready clip paths.
- First OCR implementation uses bundled ML Kit Text Recognition v2 dependencies: `com.google.mlkit:text-recognition:16.0.1` and `com.google.mlkit:text-recognition-chinese:16.0.1`.
- Bundled OCR is selected because it supports local-first first-use behavior after app install; unbundled Play Services artifacts are not the first default because first-use offline can fail while the model downloads.
- First image enhancement implementation uses Android native `Bitmap` / `Matrix` / `Canvas` / `ColorMatrix` APIs; OpenCV remains a later optional dependency if automatic boundary detection or heavier CV becomes necessary.
- Provider boundary for `TextOcrProvider`, `ImageEnhancementProvider`, and `CloudUploadPolicy` is approved for `0.2.x`.
- `FormulaOcrProvider`, `TranscriptionProvider`, `SummaryProvider`, and `ReferenceLookupProvider` may be interface-only placeholders or deferred names, but must not ship real functionality in `0.2.x`.
- `Research Reconstruction` is a completed-seminar workspace for photo enhancement, OCR review/edit, tags, key slides, search, and processing retry/cancel. It does not replace Timeline and must not fake transcript/reference/AI features.

## 2026-08-30 Phase C Local Image Enhancement Foundation Result

The local image enhancement foundation is implemented:

- `ImageEnhancementProvider` is now a production boundary for local rotate, crop, perspective correction, readability enhancement, and JPEG output.
- `AndroidBitmapImageEnhancementProvider` uses Android native `Bitmap`, `Matrix`, `Canvas`, and `ColorMatrix` APIs. No OpenCV dependency is introduced in this batch.
- `EnhancePhotoAssetUseCase` preserves the original photo, creates a deterministic app-private `enhanced/` output, records a `PHOTO_ENHANCED` derived asset, and writes durable `IMAGE_ENHANCEMENT` job success/failure state.
- The output path is variant-key based, so retrying the same enhancement options returns the existing derived asset instead of creating duplicate assets.
- JVM tests cover success, original preservation, idempotent same-variant behavior, provider failure, retryable job failure state, and cleanup of partial output.
- This batch is verified only with WSL headless unit/build/lint. Windows Emulator connected regression and UI smoke remain required before declaring full `0.2.x` complete.
