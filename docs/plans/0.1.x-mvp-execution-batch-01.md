# SeminarArc 0.1.x MVP Execution Batch 01

## Goal

Deliver the first real implementation batch through `0.1.1`:

- Android project baseline
- Compose theme and design tokens
- Room schema and repository contracts
- Seminar CRUD
- Abstract PDF import / replace / remove
- Seminar list, editor, and detail screens

This batch does **not** claim recording, CameraX capture, clip generation, or final MVP acceptance.

## Inputs And Constraints

- Product source of truth: `TODO.md`
- Release scope: `docs/plans/0.1.x-mvp-implementation-plan.md`
- Visual and interaction baseline: `design/`
- Project-local Android/Compose guidance: `AGENTS.md`, `.agents/skills/android-lead/`, `.agents/skills/compose-expert/`

Non-negotiable constraints carried into this batch:

- Every future asset must belong to a valid `seminarId`
- Schema must already support `ACTIVE`, `RECORDING`, timeline offsets, and clip states
- UI cannot rely on static mock screens or fake completion paths
- The repository must stay on the `0.1.x` line
- No true device validation in this batch

## In Scope

- Gradle and Android app scaffolding
- Manifest, application class, dependency graph, and app shell
- Material 3 theme mapped from `design/DESIGN_TOKENS.md`
- Room database, entities, converters, DAO queries, and repository implementations
- App-private media storage manager for seminar-owned files
- Seminar library, create/edit, and detail flows
- Search, filter, favorite, rating, delete, and seminar metadata editing
- PDF import and owned file lifecycle
- Batch-appropriate docs and CI skeleton

## Out Of Scope

- Foreground recording service implementation
- Notification recording controls
- CameraX photo capture flow
- Timeline event creation during recording
- Clip generation and playback fallback
- Emulator or physical-device acceptance testing
- Any AI, OCR, transcription, or cloud features

## Validation

- Build scripts and Android project structure are internally consistent
- The app shell can compile in principle with the declared dependencies
- Seminar CRUD flows are backed by Room, not in-memory fake data
- PDF attachment lifecycle goes through the storage manager
- Tests exist for seminar CRUD and storage cleanup boundaries

## Risks

- The repo currently lacks build files entirely, so dependency/version issues may surface late
- Local build verification may be limited if Gradle wrapper or Android dependencies are unavailable on this machine
- `0.1.2` placeholders must remain explicit and non-deceptive

Default next batch is `0.1.2`:

- foreground recording service
- one-active-seminar invariant enforcement
- recovery flow
- full-recording playback
