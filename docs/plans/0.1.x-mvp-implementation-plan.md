# SeminarArc 0.1.x MVP Implementation Plan

## Summary

This document records the agreed implementation plan for the SeminarArc MVP.

The target is a complete local-first Android MVP delivered within the `0.1.x` line only. The version series must not enter `0.2.x` during this implementation cycle.

Planned milestone versions:

- `0.1.0`: project baseline, build setup, dependency management, repo structure, and documentation skeleton
- `0.1.1`: seminar data layer, library, create/edit/detail flows, and abstract PDF attachment
- `0.1.2`: foreground recording service, one-active-seminar enforcement, recovery flow, and full-recording playback
- `0.1.3`: mark/note/question/photo capture and the unified timeline
- `0.1.4`: clip generation, retry/failure handling, and full-recording fallback behavior
- `0.1.5`: testing, documentation, CI, hardening, and final MVP acceptance closure

The default release target is `0.1.5`.

## Architecture And Implementation Changes

### Engineering baseline

- Keep a single Android app module: `app`
- Use Kotlin, Gradle Kotlin DSL, Version Catalog, Jetpack Compose Material 3, Navigation Compose, Room, Hilt, Coroutines/Flow, CameraX, Media3, and WorkManager
- Use `minSdk = 26`
- Set `compileSdk` and `targetSdk` to the latest stable SDK available in the environment at implementation time
- Use package name `com.yuukias.seminararc`
- Keep the layered package structure under:
  - `data`
  - `domain`
  - `recording`
  - `media`
  - `ui`
  - `worker`
  - `di`
  - `util`

### Core interfaces to establish before feature work

- `ClockProvider`
- `RecorderController`
- `ClipGenerator`
- `PhotoCaptureGateway`
- `MediaStorageManager`
- `SeminarRepository`
- `RecordingRepository`
- `TimelineRepository`
- `ClipRepository`

UI and ViewModels must depend on interfaces or use cases rather than direct platform APIs.

## Product Model And Required Behavior

### Required Room model

Implement the following core entities and relationships:

- `SeminarEntity`
- `RecordingEntity`
- `TimelineEventEntity`
- `AudioClipEntity`

Required enum/value sets:

- `SeminarStatus = DRAFT | ACTIVE | COMPLETED`
- `RecordingState = RECORDING | COMPLETED | FAILED`
- `TimelineEventType = MARK | PHOTO | NOTE | QUESTION`
- `ClipState = PENDING | PROCESSING | READY | FAILED`

Required rules:

- Every captured object must have a valid `seminarId`
- At most one seminar may be active at a time
- Starting a second seminar while one is active must route the user back to the active session
- Every event captured during a recording must store `offsetMs`
- A clip must not be presented as playable until it is actually `READY`

### Storage layout

Use app-private storage with a central storage manager and a stable directory structure:

```text
files/
  seminars/
    <seminar-id>/
      abstract/
      recordings/
      clips/
      photos/
```

Store relative paths where practical so future internal migrations remain possible.

Required cleanup behavior:

- Replacing or removing an abstract PDF deletes the old owned file
- Retaking a photo deletes the rejected capture
- Deleting a timeline event deletes its owned artifact when applicable
- Deleting a seminar removes its database records and owned media
- Failed clip generation may delete partial clip output only
- Full recordings must never be deleted because one clip failed

## Feature Delivery Sequence

### `0.1.0` Foundation

- Initialize the Android Studio project
- Add Gradle wrapper, Kotlin DSL configuration, version catalog, and baseline Android app configuration
- Add manifest, base resources, themes, app icon wiring, and dependency skeleton
- Add documentation skeletons:
  - `README.md`
  - `docs/ARCHITECTURE.md`
  - `docs/PRIVACY.md`

### `0.1.1` Seminar CRUD and PDF import

- Implement Room schema, DAOs, repositories, and storage manager
- Implement seminar library screen
- Implement seminar create/edit flow
- Implement seminar detail screen
- Implement search by title/speaker
- Implement filters for `All`, `Draft`, `Completed`, and `Favorites`
- Implement rating and favorite controls
- Implement abstract PDF import via `ACTION_OPEN_DOCUMENT`
- Copy imported PDFs into app-private storage and expose replace/remove flows

### `0.1.2` Recording session

- Implement foreground recording service
- Persist recording state in Room
- Show an ongoing notification with:
  - app name
  - seminar title
  - elapsed time or active state
  - mark action
  - return-to-session action
- Recover UI from Room plus service truth rather than Activity memory
- Implement stale `ACTIVE` recovery screen for abnormal stop conditions
- Implement full-recording playback with Media3

Default decision for this cycle:

- Do not implement pause/resume recording unless it proves technically stable across lifecycle and recovery scenarios
- Do not place a direct notification stop action unless it supports a safe, unambiguous flow

### `0.1.3` Timeline and captures

- Implement active-session UI with:
  - `Mark moment`
  - `Capture slide`
  - `Add question`
  - `Quick note`
  - `End seminar`
- Implement CameraX photo capture flow with preview, `Keep`, and `Retake`
- Preserve correct photo orientation
- Create `PHOTO`, `NOTE`, `QUESTION`, and `MARK` events on the shared timeline
- Implement chronological timeline ordering by `offsetMs`
- Implement `Play from here` for every event type

### `0.1.4` Clip generation

Clip defaults:

- pre-roll: `60_000` ms
- post-roll: `90_000` ms

Required behavior when marking:

- Create a `MARK` event immediately
- Compute:
  - `startOffsetMs = max(0, markOffsetMs - 60_000)`
  - `endOffsetMs = markOffsetMs + 90_000`
- Create a pending clip record immediately
- Delay generation until the post-roll window is safely available or the seminar ends
- Use WorkManager to generate a real standalone clip after the source audio is readable/finalized
- Clamp clip end offset to the actual recording duration
- Do not merge overlapping marks silently
- If clip generation fails, preserve the mark and fall back to playback from the full recording at the correct range

### `0.1.5` Hardening and release closure

- Add remaining automated tests
- Verify rotation, backgrounding, lock screen, process recreation, permission denial, and storage error scenarios
- Finalize `README.md`, `docs/ARCHITECTURE.md`, and `docs/PRIVACY.md`
- Add GitHub Actions to build the debug APK and run unit tests on `push` and `pull_request`
- Remove dead code, demo-only shortcuts, and unimplemented controls that could misrepresent completion
- Close the final MVP only after the full acceptance scenario succeeds

## Required Screens

The MVP must include:

- Seminar library
- Create/edit seminar
- Seminar detail
- Active session
- Post-seminar review

Required review behavior:

- Show the full recording duration and playback controls
- Show all timeline events ordered by `offsetMs`
- Show photos
- Show mark clip states
- Show notes and questions
- Support deleting an event
- Support editing note/question text
- Support replaying the full recording from an event timestamp
- Support replaying a ready clip
- Support retrying failed clip generation

## Testing Plan

### Unit tests

At minimum cover:

- mark interval calculation near recording start
- mark interval calculation near recording end
- timeline ordering
- one-active-seminar invariant
- seminar deletion cleanup orchestration
- stale active-session recovery decision

### Room tests

At minimum cover:

- seminar with recording/events/clips relationships
- foreign keys and deletion behavior
- timeline query ordering

### UI tests

At minimum cover:

- create seminar and see it in the library
- start a seminar using a fake recording controller
- add a mark, note, and question
- end seminar and reach the review screen

Testing rule:

- Abstract recorder, camera launcher, clock, and clip generation behind interfaces so tests do not require real hardware

## Acceptance Criteria

The implementation is not complete until a clean install can demonstrate the full flow:

1. Create a seminar titled `Domain Adaptation Seminar`
2. Attach an abstract PDF
3. Start the seminar and grant required permissions
4. Lock or background the app while recording continues through the foreground service
5. Return and create at least two marks
6. Capture at least one slide photo
7. Add one question and one quick note
8. End the seminar
9. See every item under the same seminar in chronological order
10. Open the photo and play the recording from its timestamp
11. Play each generated marked clip, or visibly fall back to the correct full-recording range if generation is pending or failed
12. Close and reopen the app and confirm all data and media remain accessible
13. Delete the seminar and confirm records and owned media are removed
14. Run the documented build and test commands successfully from a clean checkout

## Explicit Non-Goals

The MVP must not spend time on:

- Notion sync
- cloud backup or login
- speech-to-text transcription
- AI summaries
- PDF metadata extraction
- OCR or LaTeX recognition
- slide perspective correction
- knowledge graphs
- speaker diarization
- collaboration
- iOS or web versions

These may be documented as future work, but the app must not include placeholder UI that pretends they already function.
