# SeminarArc 0.1.4 Clip Playback Resilience Plan

Status: planned

Target version: `0.1.4`

## Goal

Implement marked audio clip generation with durable processing states, retry behavior, and full-recording fallback.

The goal is not merely to show clip UI. A clip is playable only when the app has produced a real, readable clip artifact.

## Inputs

- Completed `0.1.3` capture and timeline gate.
- Existing `AudioClipEntity`, `ClipState`, `ClipDao`, and `ClipGenerator` contract.
- Existing full recording playback.
- `docs/plans/0.1.x-mvp-implementation-plan.md` clip defaults.
- Android WorkManager guidance.

## Scope

In scope:

- Clip interval calculation.
- Pending clip record creation for marks.
- WorkManager-backed clip generation.
- `PENDING`, `PROCESSING`, `READY`, `FAILED` state display.
- Retry failed clip generation.
- Full-recording fallback for pending/failed clips.
- Cleanup of partial clip files without deleting source recordings.
- Tests for interval calculation and failure behavior.

Out of scope:

- Transcription.
- Audio enhancement.
- Speaker diarization.
- Cloud processing.
- Auto-merge of overlapping clips.
- Paid/export-specific clip transformations.

## Clip Contract

Defaults:

- Pre-roll: `60_000` ms.
- Post-roll: `90_000` ms.

When a mark is created:

- Create the `MARK` timeline event immediately.
- Compute `startOffsetMs = max(0, markOffsetMs - 60_000)`.
- Compute `endOffsetMs = markOffsetMs + 90_000`.
- Create an `AudioClipEntity` in `PENDING`.
- Delay generation until the post-roll window is available or the seminar ends.
- Clamp end offset to actual recording duration.
- Do not merge overlapping marks silently.
- Preserve the mark if clip generation fails.

## Work Breakdown

### 1. Interval calculation use case

Implement or audit a pure Kotlin interval calculator:

- Near recording start.
- Near recording end.
- Mark after known duration.
- Post-roll not yet available.
- Invalid negative or missing duration inputs.

Validation:

- JVM unit tests for all boundary cases.

### 2. Clip processing model

Define:

- Unique WorkManager naming by clip ID.
- State transitions from `PENDING` to `PROCESSING` to `READY` or `FAILED`.
- Retry count and readable error message.
- Cancellation semantics if the seminar is deleted.

Validation:

- Repository/worker tests with fake `ClipGenerator`.

### 3. Worker implementation

Implement:

- Worker input data using clip ID, not raw paths as the source of truth.
- Worker reloads clip/recording/seminar records from Room.
- Worker validates source recording exists and is finalized.
- Worker writes output under `files/seminars/<seminar-id>/clips/`.
- Worker updates Room only after output is readable.
- Worker deletes partial output on failure.

Validation:

- Failure does not delete full recording.
- Missing source recording produces `FAILED` with fallback available if possible.

### 4. Timeline and playback UI

Implement:

- Clip state labels.
- Play clip action only for `READY`.
- Retry action for `FAILED`.
- `Play from full recording` fallback for `PENDING`, `PROCESSING`, and `FAILED`.
- Loading/progress state that does not block timeline browsing.

Accessibility:

- Clip state must be text-readable.
- Play/retry/fallback actions have clear content descriptions.

### 5. Cleanup and deletion

Verify:

- Deleting a mark removes its clip record and owned clip file.
- Deleting a seminar cancels outstanding clip work and removes owned clips.
- Failed partial files are safe to remove.
- Full recordings are never deleted because one clip fails.

## Verification Gate

Do not start `0.1.5` until:

- Clip interval calculation has unit coverage.
- WorkManager can generate a real clip in a documented local scenario, or failure is recorded with actionable diagnostics.
- Timeline never offers playback for a non-`READY` clip.
- Fallback playback from full recording works for pending/failed clips.
- Cleanup behavior is tested for clip and seminar deletion.

## Risks

- Android media trimming APIs may vary by format; implementation may require a small technical spike.
- WorkManager tests can be brittle without careful fake dependencies.
- Overlapping mark behavior may need later UX refinement, but this phase should not auto-merge silently.
