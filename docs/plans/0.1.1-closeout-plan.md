# SeminarArc 0.1.1 Closeout Plan

Status: planned

Target version: `0.1.1`

## Goal

Turn the current `0.1.1-dev` foundation into a verified baseline before any recording or CameraX work begins.

This is a closeout/audit plan. It may lead to small fixes during later implementation tasks, but the plan itself does not authorize code changes.

## Scope

In scope:

- Build and dependency verification.
- CI workflow verification.
- Room schema and DAO audit.
- Repository and storage lifecycle audit.
- Seminar list/editor/detail flow audit.
- Abstract PDF import, replace, remove, and deletion cleanup audit.
- Placeholder and future-feature UI review.
- Basic accessibility and large-text review for existing screens.
- Documentation alignment with actual behavior.

Out of scope:

- Foreground recording implementation.
- CameraX photo capture.
- Timeline event creation during active recording.
- Clip generation.
- OCR, transcription, summary, Notion, AI, ads, or cloud features.
- New schema for future Research Reconstruction.

## Work Breakdown

### 1. Environment and build audit

Verify:

- Gradle wrapper files are present and usable.
- `compileSdk`, `targetSdk`, and dependency versions resolve in the local environment.
- `./gradlew assembleDebug` succeeds or fails with actionable diagnostics.
- `./gradlew testDebugUnitTest` succeeds or fails with actionable diagnostics.
- `.github/workflows/android.yml` runs meaningful build/test commands and emits useful logs.

Expected output:

- A build status note in the later task result.
- Any fixes needed are recorded as separate implementation items before moving to `0.1.2`.

### 2. Room and repository audit

Verify:

- `SeminarEntity`, `RecordingEntity`, `TimelineEventEntity`, and `AudioClipEntity` match the `0.1.x` capture model.
- Foreign keys and delete behavior cannot leave app-owned orphan records.
- DAO queries return stable counts for photos, clips, and recording duration.
- Repository methods keep database and storage operations in one orchestrated path.
- No UI layer reads Room directly.

Expected output:

- Confirmation that schema version 1 can support `0.1.2` and `0.1.3`.
- A list of required fixes if repository/storage cleanup can leave inconsistent files.

### 3. Existing UI audit

Verify:

- Seminar list remains list-first and does not become a dashboard.
- Editor creates/edits real Room-backed seminars, not mock data.
- Detail screen clearly labels `Start seminar (0.1.2)` or similar future behavior without pretending recording works.
- Delete confirmation names the seminar and owned asset classes.
- Search, filters, favorite, rating, and abstract attachment behavior match README claims.
- Public composables use Material 3 and SeminarArc tokens rather than hardcoded styling.
- Large-text and TalkBack-critical elements have a minimum 48dp target and useful labels.

Expected output:

- A small bug list with file references.
- No redesign beyond fixing misleading or broken existing behavior.

### 4. Documentation closeout

Verify and update, when later authorized:

- `README.md` describes only real current behavior.
- `docs/ARCHITECTURE.md` accurately describes current layering and future surfaces.
- `docs/PRIVACY.md` mentions current local storage and future microphone/camera permissions without implying implemented recording.
- `design/README.md` uses repository-relative links instead of machine-specific absolute paths.

## Verification Gate

Do not start `0.1.2` until:

- Build and unit-test status is known.
- CI workflow has been reviewed or fixed.
- Existing `0.1.1` UI does not show fake working recording/photo/clip behavior.
- Abstract PDF lifecycle has at least one automated or manually documented validation path.
- Known issues are either fixed or explicitly carried into the first `0.1.2` task.

## Risks

- The local environment may lack Android SDK packages or network access for dependency resolution.
- Instrumentation tests may need emulator or device setup; if unavailable, record that as a gate for later.
- Some UI placeholders are acceptable only if they are explicit future-contract labels, not simulated functionality.

## Suggested First Task

Create `prompts/tasks/0.1.1_closeout_audit_task.md` to run the build/test audit, inspect the current code paths, and write a result with actionable fix items. Allow shell commands and code reading; allow code edits only if the user wants immediate repair in that same task.
